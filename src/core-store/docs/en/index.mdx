# core-store

<Badge>Product</Badge> <Badge>Paid</Badge>

`core-store` is a complete e-commerce product: a storefront, cart, checkout,
order management, shipping and tax, discounts, wishlists, reviews, returns, and
EU-compliant invoicing — all wired into the Indigo dashboard.

## What it does

- Product catalog with **simple**, **variable**, **digital**, and **subscription** product types
- Server-side cart for both anonymous (`sessionId` cookie) and logged-in users, merged on login
- Checkout pipeline — subtotal → discount → shipping → tax — with server-validated discount codes
- Order management, status emails, customer order history, and TSV/JSON export
- Wishlists, 1-5 star reviews with verified-purchase detection and a moderation queue
- Filterable product attributes, related/upsell/cross-sell relations, and inventory alerts
- Returns, refunds, abandoned-cart recovery, and print-ready PDF invoices

## Installation

`core-store` is a paid module and requires a valid Indigo license.

```bash
bun run indigo add core-store
bun run db:generate
bun run db:migrate
```

`core-store` **requires `core-payments`** for checkout. `core-subscriptions` is
optional, enabling subscription products.

## Configuration

Dependency injection is configured in `config/deps/store-deps.ts` (scaffolded
on install) via `setStoreDeps()`:

| Dependency | Required | Purpose |
|---|---|---|
| `createPaymentCheckout` | Yes | Start a payment session (via `core-payments`) |
| `resolveOrgId` | Yes | Resolve the order's organization |
| `getBillingProfile` | Yes | Billing details for tax and invoices |
| `sendNotification` | Yes | In-app order notifications |
| `enqueueTemplateEmail` | Yes | Transactional order emails |
| `createSubscriptionCheckout` | No | Checkout for subscription products |

`setRefundHandler()` optionally registers a payment refund handler (e.g. a
Stripe refund) — see *Refunds* below for the contract.

The `seedStore` step creates demo products, shipping zones, and tax rates on
`bun run init`.

## Refunds

Every refund path is **claim → gateway → commit** (`lib/refund-service.ts` is
the shared plumbing), and `store_orders.refundedCents` is the single ledger.
Three paths write to it, so together they can never refund more than the
order total:

| Path | Claim | Amount |
|---|---|---|
| Return refund (`storeReturns.processRefund`) | return status `approved`/`received` → `refunding` (compare-and-set) **before** the gateway call | the approved return amount |
| Whole-order refund (`storeAdminOrders.refundOrder`) | the order status itself flips (compare-and-set on a paid status + the prior `refundedCents`) | `total − refunded` |
| Provider-initiated `payment.refunded` webhook | one `UPDATE … WHERE status <> 'refunded'` | settles `refundedCents = totalCents` |

The ledger is bumped only under `refundedCents + amount <= totalCents`, so a
double click or a retried request reaches the gateway once and an over-refund
is impossible by construction. `approveReturn` caps the amount at
`total − refunded − other pending returns`; `receiveReturn` / `rejectReturn`
refuse once a refund is in flight or done. An order becomes `refunded` only
when `refundedCents == totalCents`, otherwise `partially_refunded`.

### Refund handler contract

Your `RefundHandler` decides what the claim does next:

- resolve `{ refundId, status: 'succeeded' }` — money moved; the ledger is bumped and a status event recorded.
- resolve `{ status: 'failed', failureReason }` — a definitive decline; the claim is rolled back (return → `approved`, order → its previous status) and can be retried.
- **throw only when the outcome is unknown** (timeout, 5xx) — the claim is **kept** and never auto-retried, because a retry could refund twice.

### Resolving a stuck refund

A kept claim is visible as a return in `refunding`, or an order in `refunded`
whose `refundedCents < totalCents`. An admin checks the provider dashboard and
resolves it:

| Procedure | Scope | `outcome` |
|---|---|---|
| `storeReturns.resolveStuckRefund({ returnId, outcome })` | return in `refunding` | `refunded` — the money moved; runs the normal commit. `release` — nothing moved; back to `approved`, ledger untouched |
| `storeAdminOrders.resolveStuckRefund({ orderId, outcome, providerRefundId?, note?, restoreStatus? })` | order `refunded` with `refundedCents < totalCents` | `refunded` — commits `total − refunded` exactly like a normal success (ledger bump + status event; `providerRefundId`/`note` are recorded). `release` — order goes back to `restoreStatus` if given (`processing`, `shipped`, `delivered`, `partially_refunded`), else inferred: `partially_refunded` if the ledger is non-zero, `delivered` if `deliveredAt` is set, `shipped` if `shippedAt` is set, otherwise `processing`; ledger untouched, order refundable again |

Both compare-and-set on the claim as read (status + `refundedCents`) and throw
`CONFLICT` if it was resolved concurrently; an order that is not in `refunded`
is `CONFLICT` too, and one already settled in full is `BAD_REQUEST`. Every
resolution is audit-logged with the acting admin: `store.order.refund_confirmed`
or `store.order.refund_released` (entity `store_order`, with amounts, final
status, provider refund id and note in the metadata).

## API

`core-store` registers 16 tRPC routers. The principal ones:

| Endpoint | Access | Purpose |
|---|---|---|
| `storeProducts` | public + admin | Product list/detail and admin CRUD, variants, categories |
| `storeCart` | public | Cart for anonymous and authenticated users |
| `storeCheckout` | protected | Shipping options, totals preview, place order |
| `storeOrders` | protected + admin | Customer order history and admin order management |
| `storeAdminOrders` | admin | Export, whole-order `refundOrder`, `resolveStuckRefund`, and invoice generation |
| `storeWishlist` | protected | Toggle, list, check, and batch-check |
| `storeDiscounts` | public + admin | Public code validation, admin CRUD |
| `storeReviews` | public + protected + admin | List/ratings, create, and moderation |
| `storeRelations` | public + admin | Related products — get and admin set |
| `storeAttributes` | public + admin | Filterable attribute list and admin CRUD |
| `storeAddresses` | protected | Customer address book |
| `storeReturns` | protected + admin | Return requests, approval, refund processing, `resolveStuckRefund` |
| `storeFulfillment` | admin | Shipments and shipment items |
| `storeAnalytics`, `storeAlerts`, `storeAdmin` | admin / mixed | Store analytics, stock alerts, admin tooling |

## Integration

Installing scaffolds the storefront (`/store`, `/cart`, `/checkout`,
`/order-confirmation`), account pages (orders, wishlist, addresses), the
dashboard store admin pages, the payment webhook handler
(`app/api/webhooks/store/route.ts`), and a set of order email templates. A
**Store** entry is added to the dashboard *Content* group.

EU compliance is built in: per-country tax classes, `priceIncludesTax`,
reverse charge for B2B, sequential `INV-YYYY-XXXXX` invoice numbers, and a
per-item tax breakdown. An abandoned-cart maintenance task emails reminders for
24h-idle carts.
